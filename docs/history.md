## R3 — 검색·웹·이해관계자

**바꾼 계약** (구버전 → 현재)

| 구버전 | 현재 | 이유 |
|---|---|---|
| RRF 기본, 번역 LLM 호출 | dense 코사인만 | 하이브리드의 이득을 잰 적이 없다. 측정 근거가 생기면 도입 |
| 필터 후 상위 후보 부족 가능 | 컬렉션 전체 검색 후 필터 | 비대칭 코퍼스에서 한 기술이 top_k 밖으로 밀린다 |
| LLM이 collection/perspective 선택 가능 | `bind_document_search`로 Python이 고정 | 시장 근거를 papers_core에서 찾으면 기술 서술이 시장 주장 근거로 놓인다 |
| 검색 snippet을 사실 근거로 전달 | 본문 수집 성공 자료만 | snippet은 원문 위치를 댈 수 없다 |
| `data/web_cache` 전역 공유 | `runs/<run_id>/web/` | §7 *노드 실행 전에는 해당 실행의 자료만 사용* |
| URL 목록을 citations로 일괄 지정 | Claim별 evidence_ids | 주장 단위로 검증할 수 없다 |

**리뷰에서 잡은 결함**

- LLM이 빈 객체 `{}`를 반환하면 정상 평가 보류로 넘어갔다 → claims/gaps 필수 필드.
- 검색 서비스 전체 장애를 자료 부재(partial)로 처리했다 → 수집 자체를 못 하면 failed.
- 페이지를 가져오기만 하면 보완 검색을 건너뛰었다 → 초안의 근거 공백에서도 한 번 보완.
- 입력이 길면 모든 근거를 모델에 넣었다 → 총 문자 상한, 제외된 근거는 인용 금지.
- HTTP 200을 돌려주는 접근 검증 페이지를 본문으로 읽었다 → 대표 오류·검증 제목 차단.
- 웹 ID가 64자였을 때 모델이 끝 글자를 흘려 인용 검증이 실패했다 → 12자로 축소.

## R1 — 그래프·State·실행 제어

State는 §7 표를, 그래프는 부록 A의 Mermaid 소스를 그대로 옮겼다. 판단이 필요했던 지점:

- **검토 대기에서 실행을 멈춘다.** 부록 A의 `save_draft → review` 엣지를 그대로 두면 사람의
  검토 없이 무한히 돈다. `interrupt_after=["save_draft"]`로 정지하고, 실행 간 상태는
  checkpointer가 아니라 파일(`draft.json`)로 넘긴다 — 실행 사이에 사람의 시간이 끼기 때문이다.
- **병합 오류는 그래프 분기가 아니라 예외다.** 어긋난 근거로 종합·검토에 LLM을 태울 이유가 없다.
- **`gaps`는 최상위 필드다.** 레지스트리 안에 두면 종합 노드가 `collect_evidence` 소유
  필드를 건드리게 된다.
- **`collect_evidence`는 기술 조사까지 다섯 Assessment를 병합한다.** §8이 참고문헌을 실제
  인용에서 역으로 만들라고 했으므로 기술 조사 근거도 레지스트리에 있어야 한다.
- **`fail`은 `report`를 쓰지 않는다.** §8 *제출용 출력을 막는다.*

## 통합 #13 — 파이프라인이 한 번도 끝까지 돈 적이 없었다

R1~R5가 각자 main에 들어왔고 테스트 82개가 통과했다. 각 테스트가 손으로 만든 state로 자기
함수만 불렀기 때문이다. 실제로 연결하자 일곱 군데가 어긋나 있었다.

| # | 증상 | 처리 |
|---|---|---|
| ① | 그래프에 실물 노드가 하나도 안 붙어 있었다(스텁 8개) | 배선 |
| ② | `market`이 구버전 관점 dict를 반환 | Assessment로 이행 |
| ③ | `synthesis`가 Gap(dict)을 `set()`에 넣어 TypeError | 입력 형식 교체 |
| ④ | `report`가 없는 필드를 읽음 | Claim 기반으로 재작성 |
| ⑤ | `review` 노드 진입점이 없음 | 신설 |
| ⑥ | **검증 결과가 State에 안 실림** — `final_check`가 무효 인용을 못 보고 completed | `validation` 필드로 반환 |
| ⑦ | `publish` 구현 없음 | 신설 |

⑥이 가장 위험했다. 죽지 않고 조용히 통과했다.

**계획보다 컸던 부분**

- "market만 구버전"이라 봤지만 research·maturity·domain도 Assessment 조립에서
  ValidationError로 죽고 있었다(`technology="both"` 오용, 빈 `evidence_ids`, 가설에
  explanation 없음, `allowed_uses=["domain_assessment"]`, 쓰지 않는 LLM이 API 키를 요구).
- `Synthesis.conflicts`의 `min_length=1`과 `Conflict.favors`가 §5 *상충하는 의견을 억지로
  만들지는 않는다*와 어긋나 제거했다.
- 근거 공백을 §5.3에서 §6으로 옮기고, §10이 요구하는 조사 시점·검토 범위를 §6에 추가했다.
- 같은 청크를 여러 노드가 인용하면 `allowed_uses`만 달라 병합 오류가 났다 → 합집합.

**설계서와 코드가 어긋난 지점** (PDF 기준으로 정함)

| 항목 | 결론 |
|---|---|
| `validation_round` State 필드 | 없앤다 — 부록 A *재시도는 노드 내부의 최대 1회* |
| `tech_status` | §7 표에 없다 → Assessment `status`·`gaps`로 대체 |
| 형식 검사와 내용 검토 노드 분리 | 부록 A는 한 노드 → `review`가 `validate`를 부른다 |
| REFERENCE 신형·구형 두 경로 | §8 *실제 포함된 Claim의 근거에서 역으로* → 신형만 |

## 재현성 — 조사했고, 목표를 접었다

원래 목표는 *같은 코퍼스로 다시 돌리면 같은 주장이 나오고 검토 판정이 이월된다*였다.

**흔들리는 축과 처리**

| 축 | 처리 |
|---|---|
| 임베딩 revision이 `main` | 커밋 해시로 고정 ✅ |
| 코퍼스 재다운로드 (`turboquant-blog` 해시가 실제로 한 번 바뀜) | 기본 해시 검증, `--refresh` 명시 시에만 재수집, `setup`이 대조 ✅ |
| LLM 샘플링 | seed 고정 시도 → 실패 → 응답 캐시로 대체 |
| 웹 근거 | 원리적으로 재현 불가 (재생은 계약 위반이라 보류) |

**실측 (2026-09-22)** — seed 적용 후 같은 코퍼스로 재실행. 이월 0건.

| 노드 | 인용 근거 | 본문 유사도 |
|---|---|---|
| research | 9건 → 11건 | 0.282 |
| **maturity** | **5건 동일** | **0.258** |
| market | 3건 → 2건 | 0.081 |

maturity는 인용 근거가 완전히 같은데 본문이 74% 달랐다. 원인은 `langchain_openai`가
`gpt-5.6-luna`를 추론형으로 취급해 **`temperature`를 아예 보내지 않는** 것이었다. 설정의
`temperature: 0`은 조용히 무시됐고 seed도 무시됐다. 그래서 `SQLiteCache(".cache/llm.sqlite")`로
같은 프롬프트에 같은 응답을 돌려주게 했다. 적중 수는 `run.json`의 `llm`과 보고서 §6에 남는다.

**접은 이유** — "클론한 사람이 한 번 실행하면 PDF가 나오는가"가 구조적으로 불가능했다.
원문·캐시가 Git 제외이고, 무엇보다 **이해관계자 노드가 매 실행 웹을 새로 검색한다.** 프롬프트가
달라져 캐시가 적중하지 않고, 새 Claim이 원장에 없으니 검토 대기로 멈춘다. 웹 재생은 §7과
interface ③ *다른 실행의 캐시로 대체하지 않는다*를 어긴다. 애초에 이 파이프라인은 사람의 내용
검토를 필수로 설계됐다(§8). 검증이 목적이면 재실행이 아니라 `runs/<run_id>/` 산출물을 본다.

**유지하는 것** — 임베딩 revision 고정, 코퍼스 해시 검사, 응답 캐시, 검토 판정 원장
(`reviews/verdicts.json`). 재현성 주장이 아니라 같은 기계에서 재검토를 줄이고 조용한 드리프트를
막는 장치로서.

> 응답 캐시의 부작용: 같은 입력으로 여러 번 돌려 출력 분포를 재는 실험은 캐시를 끄고 해야 한다.

## 기준선 → 개선 (2026-10-21)

기준선 실물 실행에서 세 문제가 드러났고 고쳤다. 수치와 경위는 `docs/evidence/improved/README.md`.

- **research가 `both` Claim 하나로 뭉쳤다.** 모델이 `### 1. 개요`를 먼저 두자 `1. TurboQuant`를
  찾는 헤더 정규식이 실패했다. → research·maturity·domain을 구조화 출력(`turboquant`·`itme`·`gaps`)으로
  바꾸고 세 벌이던 조립 코드를 `common.evaluate` 하나로 합쳤다.
- **지시문의 수치가 근거 없이 Claim에 들어가 검증을 통과했다.** 검증이 ID 존재·범위만 봤고
  quote가 300자로 잘려 대조할 원문도 없었다. → `validate.numeric_errors`가 수치를 인용 원문과
  대조하고 §2 조건어를 확인한다. 노드는 생성 직후 1회 재작성한다. quote는 청크 전문.
- **처음엔 줄 단위로 대조해 다시 샜다.** 개선한 지시문의 조건 괄호에서 "128GB"가 근거 없이 옮겨졌는데,
  같은 문단의 다른 청크 그림 축 `128 MB`가 통과시켰다. → 문장(인용) 단위 대조, 다른 단위가 붙은
  숫자 배제, 지시문 조건에서 실험 설정값 제거.
- **조건어를 한 표기로만 요구했다가 실행이 막혔다.** 35.7%에 `128GB`만 요구했는데 ITME 초록은
  "beyond host memory limits"로 적는다. 원문에 없는 수치를 쓰라는 요구가 돼 수정 기회를 써도
  통과할 수 없었다. → 같은 뜻의 표기를 모두 인정한다.
- **fallback은 드물었다.** 캐시 없이 반복하니 개선 전 코드도 20회 중 0회였다. 구조화 출력의
  이점은 빈도가 아니라 fallback이 구조적으로 불가능해진 것이다. 대신 개선 전 기술별 Claim은
  20/20이 다른 기술 언급을 담았다(뒤에 붙는 요약·근거 공백 줄로 추정). 측정은 API 월 한도로
  개선 후 20회가 빠져 미완이다.
- **stakeholder ITME 근거 0건은 검색 질의 문제였다.** 약어 "ITME"만으로는 무관한 페이지가 돌아왔다.
  → 질의에 정식 명칭과 맥락어를 붙였다.

## 검색 품질 실측 (2026-10-21)

골든셋을 2문항(정답 청크 ID 없음, 스크립트가 돌지 않음)에서 28문항으로 만들었다. 정답은 원문
anchor 문구로 고정해 다시 라벨링할 수 있다.

- **가장 큰 변수는 검색 방식이 아니라 PDF 추출이었다.** 2단 학회 논문(ITME·PIM-CXL·InfiniGen)이
  공백 없이(`ITMEachievesuptoa35.7%`), 두 단의 줄이 섞인 채 색인돼 있었다. `x_tolerance=1.5`와 단별
  읽기로 고치자 dense Hit@5가 0.43 → 0.68, ITME는 0.29 → 0.71. 모든 chunk_id가 바뀌었다.
- dense vs RRF는 0.68 vs 0.75(28문항 중 2문항 차이)라 운영은 dense로 둔다.
- 한국어 질의가 약하다(ko 0.57 / en 0.79). 놓친 9문항 중 6문항이 한국어 전문 용어 질의다.

## 남은 한계

- `docs/evidence/r1`·`r3`는 mock·합성 데이터다. 배선·병합·상태 판정·저장을 검증했을 뿐
  기술 평가가 아니다.
- 수치 검증은 원문에 단위 없이 흔한 작은 정수(비트 수 2·3·4)를 구분하지 못한다. 변조로 재면
  못 잡는 경우 17건이 모두 이 종류였다. 수치가 어느 실험의 값인지는 사람이 검토한다.
- 마지막 수치 검증 수정(인용 단위 대조, `128 MB` 배제, research 조건의 실험값 제거) 뒤 실물 실행을
  하지 못했다(Gemini 월 지출 한도). `docs/evidence/improved/` 기록은 지금 검사기로 research Claim
  1건이 걸린다.
- market은 여전히 `## ①②③` 헤더 정규식으로 절을 자르고 Claim이 모두 `both`다. 항목별 구조라
  기술 분리 대상이 아니어서 그대로 뒀다.
- stakeholder는 ITME의 competitors·adopters·investors 근거를 찾지 못한다. 공개 반응이 아직
  적은 것인지 질의 문제인지 여러 번 돌려 확인하지 않았다.
- 검색 골든셋은 28문항이라 셀당 n=7~14다. RRF 도입 여부는 문항을 늘려 다시 본다.
- 한국어 질의가 영어 원문에서 약하다(dense Hit@5 ko 0.57 / en 0.79). 전문 용어가 원인으로 보이나 대책은 미측정.
- 품질 점검(`quality_checks`)은 Markdown 문자열만 본다. §9의 표·그래프 잘림은 실제 PDF를 봐야 안다.
